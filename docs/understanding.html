How Ethikit Actually Works

Every component, explained three ways: what it does, how it works mechanically, and why it's built that way instead of some simpler alternative — plus a concrete angle for talking about its real-world application.

How to use this doc This isn't meant to be read in one sitting. Part I is load-bearing — read it first, since everything else assumes it. Part II is a reference: read the evaluators you'll be asked about, skim the rest. Part V is a grab-bag of "why should anyone care" framings for whichever audience you're presenting to.
Part I

Foundations

Five pieces everything else in the project depends on. If you only have time to deeply understand one part before a Q&A, make it this one — most hard questions ("why doesn't it just...") get answered here.

The principle taxonomy

ethikit/principles.py
foundation
What it is

A single list of nine ethical-AI principles, each one tagged with which of four bodies — UNESCO, Microsoft, IBM, Google — actually publishes it, and whether it's tool_addressable: can a library measure it from data, model internals, predictions, or behavior, or does it require documentation and human review instead?

How it works

Each Principle is a frozen dataclass: id, human name, a one-line plain-English gloss, tool_addressable: bool, a list of InspectionTarget values (which part of the system a tool would have to look at — data / model_internals / predictions / behavior / process), and a list of which of the four source bodies name it. Six principles are tool-addressable (fairness, transparency, explainability, privacy, safety, inclusiveness); three are not (accountability, human oversight, sustainability & well-being) — those three are permanently excluded from every score.

Why this design

The alternative — inventing one proprietary "ethics score" — was explicitly rejected. Grounding every measured principle in four independently-published frameworks means a skeptical reviewer can trace any claim back to a real standard instead of a made-up rubric. The tool_addressable flag exists specifically so the tool can be honest about its own limits: it would be actively misleading to compute a number for "human oversight," since no library can measure whether a human is actually in the loop.

Why it works

Separating "can be measured" from "can't be measured" up front means every downstream score is provably complete on its own terms — nothing is silently missing from a profile, because the things that are missing are named and explained, not just absent.

Application angle

This is the answer to "who decided what counts as ethical here?" — nobody at this project did; UNESCO's 194-member-state recommendation, Microsoft's Responsible AI Standard, IBM's Pillars of Trust, and Google's AI Principles did, and this just harmonizes their overlap.

Core types: Dataset, EvalContext, EvalResult

ethikit/core/types.py
foundation
What it is

Three dataclasses that every other module in the project passes around. Dataset holds a scaled train/test split plus an optional sensitive attribute. EvalContext is what an evaluator actually receives: the fitted model, the dataset, and every prediction the runner already computed (y_pred, y_pred_train, y_proba, y_proba_train) so no evaluator ever calls model.predict() itself. EvalResult is what every evaluator hands back: one measurement, fully tagged.

How it works
EvalResult(
  evaluator: str, # which tool produced this
  principle_id: str, # which of the 9 principles this speaks to
  target: InspectionTarget, # data / model_internals / predictions / behavior
  metric: str, value: float, higher_is_better: bool,
  mechanism: str, # mandatory — this run's actual computation, in words
  details: dict = {} # free-form extras (per-feature attributions, etc.)
)

.as_record(model_name) flattens this into a plain dict for the results DataFrame — every row in every comparison table, radar chart, and Model Card ultimately comes from this one method.

Why this design

mechanism is not optional and has no default — every evaluator is forced to explain itself. This came from a direct architectural requirement: a score with no explanation of how it was computed is a black box, and black boxes are exactly what an ethics-evaluation tool cannot ship. Precomputing every prediction once in EvalContext (rather than letting each evaluator call the model itself) also means the model only ever gets called once per split, which matters once evaluators start doing expensive things like adversarial attacks.

Why it works

Because mechanism is a required constructor argument (not a docstring convention), it's structurally impossible to add a new evaluator that produces a number with no explanation — the class just won't instantiate. Discipline enforced by the type system beats discipline enforced by a code-review comment.

Application angle

This is the concrete answer to "how do you know this isn't just a black box" — point at any single row in any report and read its mechanism sentence aloud. It always names the actual computation, never just repeats the number.

The evaluator registry

ethikit/evaluators/base.py
foundation
What it is

An abstract base class (Evaluator) plus a two-function registry (register(), all_evaluators()). This is the entire plugin mechanism for the whole project.

How it works

A new tool is a subclass with four class attributes (name, principle_ids, supports, mechanism) and one method, evaluate(ctx) -> List[EvalResult]. At import time, each evaluator module calls register(MyEvaluator()) at file scope — the act of importing ethikit.evaluators is what populates the registry. available() lets an evaluator opt out gracefully when its optional dependency isn't installed (checked with a bare try: import x), and applies_to(ctx) lets it opt out per-run (e.g. "classification only," or "need at least 20 rows per class").

Why this design

The alternative — a big if tool == "shap": ... elif tool == "giskard": ... dispatcher somewhere in the runner — would mean every new tool requires editing code that has nothing to do with that tool. The registry pattern inverts that: the runner, the scoring layer, the coverage lookup, and every report all iterate all_evaluators() and never know or care how many evaluators exist or what they check. This has now been tested three separate times across three build phases (adding SHAP, adding Giskard, adding a real adversarial attack) without a single change to the runner.

Why it works

runner.py also wraps each evaluator's .evaluate() call in a try/except, turning any exception into an ERROR:... row rather than crashing the sweep. Combined with the registry, this means a badly-behaved third-party tool can never take down a benchmark run involving seven other, unrelated tools.

Application angle

The pitch for engineering audiences: "here's the entire interface a new ethics tool has to implement" — then show the README's ~15-line example. It fits on one screen, which is the whole point.

Data loading & the RawData / Dataset split

ethikit/data/loaders.py
foundation
What it is

Two layers: RawData (unsplit X/y, fetched or generated once) and split_dataset(raw, ...), which turns a RawData into one scaled train/test Dataset. load_adult() fetches the real UCI Adult income dataset via OpenML; if that fails (no network), it silently falls back to a synthetic dataset with a deliberately injected bias.

How it works

split_dataset fits a StandardScaler on the training rows only, then applies that same fitted scaler to the test rows. It also accepts explicit train_idx/test_idx arrays instead of drawing a fresh random split — this is the hook benchmark/cv.py uses to turn one StratifiedKFold fold into a normal Dataset, reusing the exact same scaling logic a single-split demo uses.

Why this design

Fitting the scaler on the full dataset (train+test) before splitting is a classic, subtle form of data leakage — test-set statistics quietly influence the "unseen" data's representation, inflating apparent performance. Splitting the loader into an unsplit RawData layer and a separate split_dataset() function exists specifically so that repeated cross-validation (Phase 2) could reuse the identical, leakage-safe scaling logic per fold instead of a parallel implementation that could drift out of sync.

The synthetic fallback's bias isn't incidental: a proxy feature is deliberately correlated with the sensitive attribute, and the sensitive attribute leaks directly into the label. This guarantees the fairness evaluator always has something real to catch, even fully offline.

Why it works

Because both the single-split demo and repeated CV route through the same split_dataset() call, there is exactly one place scaling logic can go wrong, and testing it once covers both code paths.

Application angle

Good talking point on rigor: "the demo runs with zero network access and still produces a real fairness violation to detect" — because the synthetic fallback was built as a test fixture with a known-ground-truth bias, not a happy-path toy.

Coverage: the reverse map

ethikit/coverage.py
foundation
What it is

Every evaluator already declares which principles it speaks to (principle_ids). This module answers the reverse question: given a principle, which registered tool(s) address it, and what does each one actually do?

How it works

principle_to_tools() loops all_evaluators() and inverts the mapping. tool_info(name) returns one evaluator's full self-description — principles, static mechanism, supported task types, current availability. Nothing here is precomputed or cached; it always reflects whatever's live in the registry at call time.

Why this design

Without this, "which tool should I run for privacy" was a question you could only answer by reading source files. Because it reads the registry directly rather than a hand-maintained list, it can never drift out of date the way a hardcoded lookup table would the moment someone adds a ninth evaluator.

Why it works

The same reverse map that answers "which tool for principle X" before a run also powers every report's "which OTHER tool could have scored this" section after a run — one small module serving both a planning question and an accountability question.

Application angle

Demonstrates tool independence to a skeptical reviewer: "safety" currently has three evaluators corroborating it from different angles (noise, adversarial search, drift) — not one opaque number, three independently-computed ones that happen to agree.

Part II

The original eight evaluators

Every principle score in this project traces back to one of these. Three are marked real attack — they don't estimate risk, they actually try to break the model and measure whether they succeeded. Six more tools arrived later; see Part VII.

Performance

ethikit/evaluators/performance.py · axis: utility (not an ethics principle)
predictions
How it works

Ordinary scikit-learn metrics against the held-out test set — accuracy, macro-F1, and ROC-AUC (if predict_proba exists) for classification; R², RMSE, and MAE for regression. No library beyond sklearn itself is required.

Why this design

Tagged with a non-canonical "utility" id, deliberately outside the nine-principle taxonomy, so it forms its own axis on every radar chart and is structurally excluded from principle_profile()'s averaging. This stops utility from silently diluting an ethics score — a highly accurate but unfair model should never look "more ethical" by proxy of being accurate.

Application angle

Every trade-off conversation in the project ("this model is 3% less accurate but its fairness gap is half the size") is only possible because utility was kept on its own separate axis instead of blended in.

Fairness

ethikit/evaluators/fairness.py · principle: fairness (+ regression branch)
predictionsfairlearn → numpy fallback
How it works

Splits test-set predictions by a declared sensitive attribute (e.g. sex) and computes two standard group-fairness metrics via fairlearn, falling back to a hand-rolled numpy implementation if fairlearn isn't installed:

demographic_parity_diff = maxg P(ŷ=1 | group=g) − ming P(ŷ=1 | group=g)
equalized_odds_diff   = max( maxg |TPRg − TPR| , maxg |FPRg − FPR| )

For regression (Phase 2), there's no "positive prediction rate" to compare, so the analogous check becomes a group error gap instead: group_mae_gap / group_mse_gap — the spread in mean absolute/squared error across groups, plus worst_group_mae.

Why this design

Demographic parity and equalized odds are two of the most-cited fairness definitions precisely because they can contradict each other — a classifier calibrated to satisfy one can violate the other by construction (this is the Kleinberg/Chouldechova impossibility result the project cites everywhere). Reporting both, rather than picking a "winner," is the point: it makes the trade-off visible instead of hiding it behind a single fairness number.

Why it works

Both metrics are flagged higher_is_better=False — a gap of 0 is perfect parity — so the generic normalize() step correctly flips them without any fairness-specific logic anywhere else in the pipeline.

Application angle

Direct fit for lending, hiring, and insurance underwriting — any domain with a legally protected class and a binary decision. "Our demographic parity gap between groups is 4%, our equalized-odds gap is 7%" is a sentence a compliance team can act on.

Explainability

ethikit/evaluators/explainability.py · principle: explainability
model_internalsSHAP → surrogate-tree fallback
How it works

Runs SHAP's permutation explainer on a sample of test rows, tuned to max_evals = 2 × n_features + 1 (the minimum SHAP itself requires for permutation attribution to be well-defined). If SHAP raises for any reason, it falls back to training a shallow surrogate decision tree to mimic the real model's predictions and reads feature importances off that tree instead — with a fidelity score (does the surrogate actually agree with the real model?) reported alongside so a reader can tell which backend actually ran.

Why this design

A raw feature-importance number is meaningless without knowing whether it's a genuine SHAP attribution or a fallback approximation of one. The evaluator's mechanism string always names which path executed and, for the fallback, includes the surrogate's own fidelity — so "explainability = 0.8" never gets read the same way regardless of which computation actually produced it.

Why it works

Because the fallback is graceful rather than a hard failure, the explainability principle never silently goes missing from a profile just because SHAP timed out or errored on one particular model.

Application angle

The GDPR "right to explanation" and similar regulatory language ask, in effect, "can you explain this decision to the person it affected" — this evaluator is the closest thing in the project to a direct, automatable proxy for that requirement.

Robustness (random noise)

ethikit/evaluators/robustness.py · principle: safety
behaviordependency-free
How it works

Adds Gaussian noise, scaled per feature (N(0, σ · feature_std)), to every numeric test row, five independent times, and measures how often the prediction stays the same (classification) or how much it shifts in relative terms (regression).

Why this design

This is intentionally the weakest, cheapest of the three safety evaluators — a baseline, not a claim of real adversarial resistance. It exists because ordinary deployment noise (sensor jitter, rounding, slightly stale features) is random, not adversarially crafted, and a model that can't survive that baseline case is a more urgent problem than one that merely fails against a dedicated attacker.

Why it works

Precisely because it's cheap and dependency-free, it runs on every model in every sweep without a runtime cost — the two more expensive Phase 3 evaluators (adversarial search, drift) exist specifically to go further where this one stops.

Application angle

"Does this model survive normal production noise" is the first, cheapest safety gate in a deployment pipeline — before anyone reaches for a real adversarial-attack tool.

Membership inference real attack

ethikit/evaluators/privacy.py · principle: privacy · Phase 3
behavior
How it works

A genuine black-box membership-inference attack (Yeom et al., 2018). For every row, extract a "how well does the model fit this point" feature:

classification: confidence_true = P(ŷ=y_true), loss = −log(confidence_true + ε)
regression:       feature = [ −(y−ŷ)², −|y−ŷ| ]

Training rows are known members (label=1); test rows are known non-members (label=0). Balance the two groups by subsampling the larger one down to match, then fit a LogisticRegression "attacker" to tell them apart from that feature alone, scored strictly out-of-fold via StratifiedKFold + cross_val_predict so the attack's own reported accuracy is never inflated by testing on rows it trained on.

attack_auc   = roc_auc_score(membership_label, out_of_fold_attack_proba)
advantage    = max(0, 2 × (attack_accuracy − 0.5))
Why this design

The project's original roadmap specified TensorFlow Privacy for this. That package's latest release (0.8.11, unmaintained since ~2023) hard-pins pandas~=1.4, which has no Python 3.12 wheel and fails to build from source — confirmed by hand. Rather than ship a weaker proxy quietly relabeled as "membership inference," the actual published attack algorithm TensorFlow Privacy itself wraps was implemented directly against scikit-learn. This is a faithful reimplementation of a real, peer-reviewed technique, not an approximation of one.

Why it works

Cross-validating the attack classifier out-of-fold is what makes the reported accuracy trustworthy — a naive "train and score on the same rows" attacker would systematically overstate how much an adversary could actually learn.

Application angle

Directly answers a GDPR/CCPA-style question: "could someone determine whether a specific person's data was used to train this model, just by querying it?" A measured 0.0 advantage is a defensible, testable answer — not an assumption.

Giskard scan

ethikit/evaluators/giskard_scan.py · principles: fairness, safety
behaviorclassification only
How it works

Delegates to Giskard's own automated scanner over a sample of test rows. PerformanceBiasDetector uses loss-guided slicing to auto-discover data subgroups where the model performs significantly worse than its global average — mapped to fairness, since it's an unlabelled analogue of the demographic-parity check that can catch disparities on slices nobody explicitly declared as sensitive. NumericalPerturbationDetector and EthicalBiasDetector perturb feature values (noise, rescaling, protected-attribute swaps) and flag high failure rates — mapped to safety. Issues are severity-weighted (major=3 / medium=2 / minor=1) and summed per principle.

Why this design

Giskard was chosen as a long-term backbone specifically because it's unified — one dependency that already extends to LLM scanning too, unlike single-purpose tools. Its data-leakage detector was deliberately left unwired at first (documented in-code) since Phase 1's privacy story was still an explicit proxy pending Phase 3's real attack — now that a real membership-inference attack exists, whether Giskard's leakage scan adds independent signal is an open question worth revisiting.

Why it works

Because it auto-discovers problem subgroups rather than requiring a human to name a sensitive attribute up front, it catches disparities the declared-attribute fairness check structurally cannot see.

Application angle

Good answer to "what if there's bias against a group we didn't think to check for" — loss-guided slicing finds underperforming subgroups without being told where to look.

Adversarial robustness real attack

ethikit/evaluators/art_robustness.py · principle: safety · Phase 3
behaviorclassification only
How it works

Wraps the fitted model as a label-only black-box oracle (art.estimators.classification.SklearnClassifier) — no gradients, no internals, exactly the access an external attacker actually has against a deployed API. Runs HopSkipJump (Chen et al., 2019): starting from a correctly-classified point, it walks toward the model's decision boundary using only the boundary's binary signal (flipped / not flipped), alternating a binary search toward the boundary with a gradient-direction estimate built from random queries near it, converging on the smallest perturbation that flips the label.

Query/iteration budgets were deliberately tightened after hand-timing the attack: at ART's own defaults, a single RandomForestClassifier took 38 seconds for just 30 samples. The tuned budget (15 samples, max_iter=10, max_eval=300) keeps a full model-zoo sweep to roughly one to two minutes.

Why this design

Complements, rather than replaces, the Gaussian-noise robustness check: random noise tests the average case, an adversarial search tests the worst case an attacker would actually find. A model can be extremely stable under random jitter and still be trivially foolable by a deliberately-crafted, tiny perturbation — these are genuinely different failure modes.

Why it works

On low-dimensional data, HopSkipJump can flip every model within budget, making the raw success-rate metric uninformative there — but the companion metric, the median perturbation size needed, still separates models clearly (0.235 vs 0.764 in one measured run), because "how big a change was required" carries information even when "was it eventually possible" doesn't.

Application angle

The direct fit is any model exposed as a queryable API — content moderation, fraud detection, spam filtering — where an adversary can iteratively probe predictions and search for an evasive input.

Drift detection real attack

ethikit/evaluators/drift.py · principle: safety · Phase 3
databehavior
How it works

A train/test split is, by construction, the same distribution — there's no real drift to find there. So this evaluator manufactures one: every feature of the test set is shifted by shift_scale × per-feature training standard deviation, sign chosen at random per feature, simulating a deployment population that has genuinely diverged from the training population. Alibi Detect's real TabularDrift — a per-feature two-sample Kolmogorov-Smirnov test with Bonferroni correction across features — is then run against both the shifted set and the original, unshifted one.

detection_score = ( [detector correctly flags shifted set] + [detector correctly clears original set] ) / 2
retention       = 1 − clip( (perf_original − perf_shifted) / |perf_original| , 0, 1 )
Why this design

Two independent questions get answered here, deliberately kept separate: does the statistical monitoring tool itself actually work on this data (a real deployment-observability question), and does the model degrade gracefully or collapse once that drift is present (a model-quality question). Conflating them into one number would hide which of the two is actually the problem.

Why it works

Bonferroni correction across features means the detector's false-positive rate stays controlled even as feature count grows — without it, testing dozens of features independently at p=0.05 each would flag "drift" on unshifted data fairly often just by chance.

Application angle

This is the MLOps pitch: any model in production needs to know when its input distribution has moved away from what it was trained on — this evaluator proves the monitoring actually catches that before it's deployed, not after.

Part III

Scale & statistical rigor

How a single model-vs-dataset check becomes a benchmark that can support a defensible "model A beats model B" claim across many folds and many datasets.

Model zoo

ethikit/benchmark/models.py
How it works

A static registry of stock scikit-learn estimators grouped by family — linear, tree_based, instance_based, probabilistic, kernel for classification, plus a mirrored REGRESSORS registry (Phase 2) so the fairness evaluator's regression branch is actually exercised rather than dead code.

Why it works

Grouping by family, not just by name, is what makes family-level comparison a meaningful question at all — the meta-benchmark and comparison table both key off family_of() to answer it.

Application angle

"Which family of model tends to be more ethical, in general" is a genuinely different — and often more actionable — question for a team than "which single model won this one run."

Runner

ethikit/benchmark/runner.py
How it works

For each model factory: fit on the training split, cache every prediction the evaluators might need into one EvalContext, then iterate every available and applicable registered evaluator, catching exceptions per-evaluator so one broken tool becomes a single ERROR:... row rather than an aborted sweep.

Why it works

This is the one place in the whole codebase that touches every evaluator — keeping it to roughly 40 lines is deliberate; almost everything it needs to know (what evaluators exist, what they need) lives in the registry and EvalContext, not here.

Repeated cross-validation

ethikit/benchmark/cv.py · Phase 2
How it works

run_benchmark_cv() runs the exact same evaluator battery across n_repeats independent shuffles of StratifiedKFold(n_splits), tagging every row with its (repeat, fold, seed). score_distribution() then pivots that into a model × (repeat, fold) matrix — one score-distribution per model, ready for a hypothesis test, instead of one point estimate.

Why this design

A real bug surfaced during testing here: some metrics (like Giskard's giskard_issue_score) are reported under more than one principle in the same run. A naive groupby on metric name alone silently averaged the fairness-bucket and safety-bucket numbers together, halving the effective sample count without any error. score_distribution() now takes an explicit principle parameter and raises a ValueError if it's needed but omitted, rather than silently producing a quietly-wrong distribution.

Why it works

This is exactly the kind of bug that a single test run would never catch (the wrong number still looks plausible) — it only surfaced because a second, differently-shaped test (regression fairness) forced a direct comparison against the expected row count.

Application angle

"We ran this once and model A won" is an anecdote; "model A won across 15 independent folds, and here's the p-value" is evidence — this is the machinery that turns one into the other.

Meta-benchmark

ethikit/benchmark/meta.py · Phase 2
How it works

Runs the full sweep once per dataset across a default suite of 10 PMLB datasets (chosen over OpenML-CC18: no API key required, reliable GitHub-hosted CSVs). aggregate_across_datasets() normalizes scores within each dataset first — so datasets with wildly different scales never distort the average — then means per model per principle across every dataset that model actually ran on.

Why it works

Normalizing per-dataset before averaging across datasets is the step that makes the cross-dataset average meaningful at all — without it, a dataset where every model scores near 1.0 could silently dominate the aggregate over one where scores are more spread out.

Application angle

Answers "does this finding generalize, or did we get lucky with Adult specifically" — the same question a reviewer would ask about any single-dataset ML paper.

Statistical significance

ethikit/scoring/significance.py · Phase 2
How it works

A Friedman test — the standard non-parametric test for comparing multiple models across multiple related samples (CV folds, or datasets) — asks whether every model's average rank is really the same, or whether the observed ranking differences are unlikely to be chance. If it rejects that null (p < 0.05), a Nemenyi post-hoc test follows up on exactly which pairs of models differ, and a critical-difference diagram renders each model's average rank on a line with a bar connecting every group that isn't significantly different from each other.

enough_data = (n_samples ≥ 5) and (n_models ≥ 3) # Demšar (2006)'s rule of thumb
Why this design

Nemenyi is deliberately gated behind Friedman rejecting the null first — running pairwise comparisons on a ranking that was never shown to differ from chance in the first place would manufacture the appearance of precision the data doesn't support. The enough_data flag exists so a p-value is never presented with more authority than the sample size backing it actually earns.

Why it works

This is the standard methodology from Demšar's 2006 "Statistical Comparisons of Classifiers over Multiple Data Sets" — reusing an established statistical procedure instead of inventing a bespoke significance heuristic is what makes the resulting claims defensible to anyone with a stats background.

Application angle

The single strongest answer, if a mentor asks "how do you know this isn't just noise": a measured Friedman result of p = 1.65e-11 on accuracy across 15 CV folds — not eyeballing two means.

Part IV

Scoring & reporting

How raw per-metric rows become a comparison table, a radar chart, and a document a human — or a regulator — can actually read.

Aggregate scoring

ethikit/scoring/aggregate.py
How it works
normalize(): scaled = (value − min) / (max − min); flip to (1 − scaled) if lower-is-better
principle_profile(): pivot_table(model × principle, mean of norm) — performance excluded
pareto_front(): model m survives unless some other model ≥ m on every objective AND > on one
weighted_score(): Σ (weighti / Σweights) × profile[i], weights supplied by a human, never defaulted
Why this design

Every one of these four functions is a small, separately-testable step rather than one opaque "score this model" call — normalize() doesn't know about principles, principle_profile() doesn't know about trade-offs, pareto_front() doesn't know about weights. The Pareto front specifically exists because it requires no human-supplied weighting at all — it answers "which models are not strictly beaten by another" using only the raw trade-off structure.

Why it works

Because weighted_score() is the only function in this module that requires a human input, and every other function works without one, the pipeline can always produce something useful (a profile, a Pareto front) even when nobody has yet decided what matters most.

Application angle

"There is no single most-ethical model" stops being a caveat and becomes a demonstrable fact once you can show a Pareto front with more than one model on it — genuinely undominated trade-offs, not a hedge.

Model Cards

ethikit/report/model_card.py
How it works

One HTML document per model, following the Model Cards schema (Mitchell et al., 2019 / Google's Model Card Toolkit): model details, intended use, quantitative analysis (every metric with its mechanism sentence), a per-principle profile, a tool-coverage section (which tool scored this principle here, and which other registered tools could have), ethical considerations (the governance-only principles this card explicitly does not cover), and caveats.

Why this design

model-card-toolkit, the real Google library, doesn't build on Python 3.12 (an absl-py pin failure) — so this is a from-scratch renderer that mirrors the published schema exactly, with a best-effort sidecar JSON export to the real library's own ModelCard dataclass whenever it happens to be importable, wrapped so any field mismatch never blocks the actual HTML deliverable.

Why it works

Governance principles are listed explicitly as not represented on every card, rather than just omitted — a reader can't mistake "no score shown" for "this was checked and found fine."

Application angle

This is the audit-trail artifact: a document a compliance reviewer, a client, or a regulator could actually be handed, that traces every number back to a specific computation.

Aggregate HTML report

ethikit/report/report.py
How it works

A single self-contained HTML file: the per-principle profile table, the Pareto-optimal model list, and a full principle × tool × mechanism coverage table — everything needed to understand one benchmark run without opening a terminal.

Application angle

The one artifact to leave open in a browser tab as your live-demo fallback — no server, no dependencies, just a file.

Streamlit demo

demo/app.py
How it works

An interactive UI over the exact same run_benchmark() call the CLI examples use — pick model families, run, and get a live Plotly radar chart, comparison table, and per-model Model Card viewer, plus an expander showing the coverage table.

Why it works

Nothing in this file hardcodes evaluator names or metrics — it discovers everything through the same registry every other consumer uses, so a new evaluator shows up in the UI automatically, with zero UI code changes.

Concrete domain scenarios
  • Lending / credit scoring — fairness (demographic parity across protected classes), explainability (adverse-action notices), Model Cards as the audit trail a regulator can request.
  • Hiring / résumé screening — fairness + Giskard's auto-discovered subgroup slicing (catches bias against groups nobody thought to declare as sensitive).
  • Healthcare risk scoring — explainability (a clinician needs to know why), robustness (noisy real-world sensor/lab data), drift (patient population shift over time).
  • Content moderation / fraud detection APIs — adversarial robustness (an attacker actively probes a public endpoint), privacy (was any user's data memorable from outputs?).
  • Any model behind a queryable API — membership inference, directly: could someone determine whether their data trained this model just by querying it?

What milestones M2-M7 added

The same registry and the same run summary, extended in six directions. Each component below is one module; TESTING.md lists the tests that hold each one to its claims.

Six more tools (14 in all)

evaluators/aif360_eval.py, calibration.py, subgroup.py, permutation.py, attribute_inference.py, captum_ig.py
predictionsmodel internalsbehavior
How it works

AIF360 adds disparate impact, equal-opportunity / average-odds differences and the Theil index. Calibration measures expected calibration error overall and its gap between groups. Subgroup performance reports the worst group's accuracy and the best-worst gap. Permutation importance gives how concentrated the model's reliance is and how much it uses the sensitive column. Attribute inference is a second privacy attack. Captum integrated gradients reads a neural network's own gradients.

ECE = Σ_b (n_b/n) · |acc(b) − conf(b)| (bins b of predicted probability)
attribute_inference_gain = max(0, AUC(features + model output) − AUC(features only))
IG_j(x) = (x_j − x'_j) · ∫₀¹ ∂f(x' + α(x − x'))/∂x_j dα, Σ_j IG_j(x) = f(x) − f(x')
Why it works this way

Every tool-addressable principle now has at least two independent tools, so no principle rests on one library's opinion. A contract test makes every tool supply a formula, a mechanism, its limits ("what this does not measure") and a worked trace, and return values in range.

Reference suites per domain

ethikit/domains/
data
How it works

A domain (census income, lending, health, ...) is a list of real public datasets with the sensitive attribute set the way the literature uses it. A suite run evaluates each model family on every dataset and reports, per family, the spread of each principle across datasets, plus a shortlist.

Why it works this way

It answers "where should I start?" before a team has its own data, as evidence across several datasets instead of one lucky split, and never as a winner: the output is a distribution per family.

Requirements, choice stability, run history

ethikit/decision.py, ethikit/runs.py
decision support
How it works

A requirement is a bound on a raw metric (demographic_parity_diff<=0.1); a model that fails any requirement, or was not measured, is excluded with the reason. Stability asks how far the weights must move before a different feasible model comes first: per principle it sweeps that principle's share of the weight from 0 to 1 (others keep their proportions), and it samples nearby weight vectors from a Dirichlet centred on today's.

share_p ∈ [0, 1], w_q ← w_q · (1 − share_p) / Σ_{r≠p} w_r (one-principle sweep)
nearby weights ~ Dirichlet(concentration · w), stability = P(same model first)
Why it works this way

Weights are a value judgement; the tool's job is to show how much that judgement matters. Every run is also saved (config + summary) so it can be re-opened, diffed against another run, or replayed exactly.

Data profile and datasheet

ethikit/profile.py, ethikit/datasheet.py
datadocumentation
How it works

Before any model: group sizes and base rates, missingness before imputation, and a proxy screen (a depth-4 tree's out-of-fold AUC at predicting the sensitive attribute from the other features, plus per-feature mutual information). The datasheet (Gebru et al.) is pre-filled from these numbers and the run config; the questions only people can answer stay open.

proxy AUC = AUC( tree(other features) → sensitive attribute ), 5-fold out-of-fold
Why it works this way

A gap that exists in the data will be learned by any model that fits it well, and dropping a column does not remove what other columns encode. Saying so up front keeps the model comparison honest.

Deep learning on tabular data

ethikit/deep.py
model internals
How it works

A small PyTorch network wrapped in scikit-learn's fit / predict / predict_proba, so every tool, the console and the model card treat it like any other model. With dp=True it trains with DP-SGD (Opacus): per-example gradients are clipped and noised, and the privacy budget actually spent is recorded. Saved PyTorch modules and Keras-style models are wrapped by adapters.

DP-SGD: g̃ = (1/B) [ Σ_i clip(g_i, C) + N(0, σ²C²) ], (ε, δ) from the privacy accountant
Why it works this way

The privacy tools needed a genuinely privacy-preserving model to compare against: on small noisy data the membership-inference advantage falls from about 0.41 to 0.05 at ε = 1, and the cost (here a wider parity gap) is visible in the other columns.

Mitigation what-if and local explanations

ethikit/mitigation.py, ethikit/explain.py
counterfactual
How it works

The what-if retrains a fairness-constrained version of a model (fairlearn's exponentiated gradient, or group-specific thresholds) and shows before / after. It is labelled a counterfactual and never changes any audit score. The row explainer sets each feature of one test row to its training mean in turn and reports how far the score moves.

Why it works this way

Teams ask "what would fixing this cost?" and "why this person?"; both answers are useful, and both are kept out of the audit so the audit only ever describes the models actually given to it.

Model Card JSON, the audit bundle, checklist provenance

ethikit/report/mct_json.py, ethikit/bundle.py, ethikit/checklists.py
documentation
How it works

Each model card is also written in Google's Model Card Toolkit JSON schema and validated against it. The audit bundle collects config, results, metrics.csv, traces, report, cards, datasheet, checklist answers and library versions with a checksum per file; ethikit bundle verify re-runs the config and compares every metric. Each governance checklist records its edition, whether it is verbatim (Deon) or a paraphrase, and when it was compared with the original.

verify ok ⇔ every checksum matches ∧ every metric reproduces (|a − b| ≤ 1e-9 · max(1, |b|))
Why it works this way

An audit a reviewer cannot re-run is a claim. The bundle turns it into evidence, and the checksums plus the re-run mean an edited number is caught twice.

Accessibility and packaging

ethikit/web/, tests/e2e/test_a11y.py, tests/test_packaging.py
usability
How it works

Every text colour meets WCAG AA in both themes (checked by axe-core on every console tab and docs page); the tabs follow the WAI-ARIA pattern (arrow keys, Home / End); reduced motion switches every animation off while the run still updates; every page prints on white with all sections expanded. The wheel carries the console and schema, and works without the source tree.

Why it works this way

A tool about inclusiveness should be usable by everyone, and a tool meant to run locally should install and run cleanly on a fresh machine.

Part VI

Six decisions that shaped everything else

If a question doesn't map to a specific component above, it probably maps to one of these.

No single ethics score, ever

Some fairness definitions are mathematically incompatible with each other (Kleinberg / Chouldechova). Collapsing everything into one number would hide that fact. A ranking only ever appears once a human explicitly supplies weights.

The registry pattern for every tool

Subclass, implement one method, register. Validated across three build phases (SHAP, Giskard, real adversarial attacks) with zero changes to the runner, scoring, or reports.

mechanism is mandatory, not optional

Every measurement is a required, human-readable sentence explaining exactly how it was computed — enforced by the constructor, not a code-review convention.

Prefer a real library; degrade gracefully

Every optional-dependency evaluator gates itself with available() and falls back rather than crashing. One broken tool never takes down a benchmark involving seven others.

One scaling code path for single-split and CV

RawData + split_dataset() exist so a single train/test split and repeated K-fold CV can never silently drift out of sync with each other.

When a real tool doesn't build, implement the algorithm — never fake the result

Happened twice: Model Cards (hand-rolled when model-card-toolkit failed to build, and since v0.2 also exported as JSON validated against its real schema) and membership inference (the real Yeom et al. attack implemented natively when TensorFlow Privacy failed to build). Never a silently-weaker proxy relabeled as the real thing.
